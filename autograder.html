From subjective reviews to explicit criteria

In one semester, four sections of Boston University's DS210, Programming in Rust, used this workflow across 130+ students and more than 1,000 student assignment repositories. I built the entire CLI while serving as a teaching assistant from January 2025 to June 2026.

Before this, we reviewed submissions manually. Assignments did not have test cases, and students in previous semesters had complained that grading was subjective and difficult to standardize across graders. GitHub Classroom did not offer the Rust-specific setup we needed. A single pass/fail result from a Cargo test run also did not give us a partial-credit rubric.

I built a tool that discovers individual tests, lets instructors configure their point values, and generates a GitHub Actions grading workflow. The same configuration produces a student-facing grading table, making the criteria visible alongside the assignment.

Discover once, configure, then generate

I used syn to parse Rust source and discover test functions, including tests inside nested modules. Instructors do not have to list each function or point the command at individual test files. Discovery writes an editable configuration; points and timeouts can be adjusted before generating the workflow.

# Discover tests and create an editable grading configuration autograder-setup init # After reviewing points and timeouts, generate the workflow autograder-setup build # Publish the same grading criteria in the assignment README autograder-setup table --to-readme
The CLI separates test discovery, grading decisions, and workflow generation. reset removes generated artifacts when an assignment needs a fresh setup.

The generated workflow runs checks with their configured point values, allowing students to earn credit for passing parts of the assignment. Generating the YAML ahead of time keeps configuration parsing out of grading runs. By default, grading uses a dispatch trigger rather than running on every push, limiting unnecessary CI runs.

Simulated run with a fixed illustrative rubric; no Rust code executes in your browser. The real CLI generates GitHub Actions workflows from discovered tests and instructor-configured point values.

I built the assignments as well as the tool

Instructors gave me assignment specifications. I wrote the function stubs and test cases, then used the CLI to turn them into autograded GitHub Classroom assignments. Students filled in the implementations against those interfaces and practiced GitHub workflows as part of the course.

That process taught me stub-driven design in practice: the interfaces had to communicate the assignment clearly and let the test suite exercise student implementations consistently. The CLI handled the repeated setup so I could focus on the assignment and its grading criteria.

Supporting how students work

After deployment, I added configurable credit for commit-count thresholds and for students writing their own tests. Those checks let an instructor include development practices alongside functional correctness in the rubric.

The project also became teaching material. Later in the semester, we used it in a lecture on modular design. Alongside teaching sections, I built interactive visuals of the repository's growth to help students in a 200-level course understand how a larger program fits together.

Continued use beyond GitHub Classroom

The DS210 implementation is now maintained by Lauren Wheelock. The course continues to use the approach through a fork adapted for Gradescope autograding outside GitHub Classroom. The original CLI remains available on crates.io, with an mdBook guide, configuration reference, and prebuilt Windows and macOS binaries.
