Semantic Connect

A way to read governed Power BI measures from Python without writing DAX, built for web apps and AI agents.

Status
In development, internal at Trinity
Stack
Python, DAX, Microsoft Fabric, Power BI, Apache Arrow
Size
More than 700 tests, a written spec, and about 30 decision records

The problem

Trinity's reporting lives in Power BI and Fabric semantic models, where every business definition is already written down as a measure. Getting those numbers out into a web app or an AI agent is the hard part, and both common routes hurt.

Asking a language model to write DAX produces queries that look right and are wrong, and it takes several rounds of correction to get a trustworthy answer. Querying the lakehouse over SQL skips the measures entirely, so the definitions get rewritten and start to drift, and the queries land on the same background capacity as pipelines and refreshes.

The approach

Semantic Connect is a small Python library that sits between the caller and the model. You describe a query by name: which measures, which columns to group by, which filters, how to sort. The library checks the request, writes the DAX itself with a single deterministic renderer, and sends it to the semantic model's REST query endpoint.

If something is wrong, such as a measure that does not exist or a sort on a column that is not in the query, it fails immediately with an error that lists what is valid. Nothing has to guess, and nothing needs the network to find out.

result = ( model.query() .measure("Revenue") .group_by("Calendar[Year]") .where("Calendar[Year]", "in", [2025, 2026]) .order_by("Calendar[Year]") .execute(backend) ) df = result.to_pandas()
Illustrative. The measure and column names are examples.

Why the REST path

Reads go through the Power BI query API and come back as Arrow, so a web app can run as a service principal with read and build access and nothing more. On a production model, the same query ran about three times faster warm (a 0.38 second median against 1.14) and about seven times faster cold than the notebook-only route, with identical results across more than 3,000 rows.

There is a capacity argument too. In Fabric, semantic model queries count as interactive operations, which are smoothed over minutes. Background work such as pipelines and warehouse queries is smoothed over a full day. An API on top of a semantic model does not have to queue behind the data engineering workload sharing the same capacity.

How it is built

The builder is immutable, and every method checks its own arguments the moment it is called. One module is the only place query text is composed, and it escapes every name and literal. Two interchangeable executors, one over REST and one over the Fabric notebook library, pass the same contract tests. Importing the package pulls in none of the heavy dependencies until a component needs one.

The project runs on decision records. Every design choice is written down with its alternatives, and the coding agents that do most of the typing can propose new decisions but cannot change an accepted one.

What comes next

Next is validation against a snapshot of the model, so a bad request is rejected before any DAX exists, and generated typed references so an editor can autocomplete tables, columns, and measures. After that comes a code generator that turns a snapshot into an MCP server, so an agent can only ask questions the model can answer.
