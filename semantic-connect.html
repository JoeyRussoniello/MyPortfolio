Semantic Connect

16 queries. Two semantic models. Under a second in our underwriting app.

StatusIn internal use; active development
StackPython, DAX, Fabric, Power BI
FocusSemantic-model queries for custom apps

From database pulls to live comparisons

I built Semantic Connect so Trinity's custom web apps can query Power BI measures without hand-written DAX. Our internal underwriting app uses it to pull financial and operating metrics for nearby assets. I have observed all 16 queries across two semantic models finish in under a second, running in parallel from a cold application backend.

Previously, the app retrieved data through database stored procedures. It can now reuse the calculation definitions maintained in our semantic models. These queries supply internal comparisons alongside the app's public market research; the timing covers the model queries only.

I built the query library, DAX compiler, execution backends, and underwriting data pull integrations, on top of the database and data engineering workloads I also own at Trinity. The library is in internal use and active development.

Why REST made this practical

The sempy notebook path I tested had roughly 10 seconds of cold-start overhead, with Fabric VM startup adding up to another 30 seconds. It also lacked the service-principal and on-behalf-of authentication flows our app needed. That made it unsuitable for interactive requests from a custom web app.

Database queries used background compute shared with our data engineering workloads. In our setup, bringing remote data into local storage incurred fixed 60-second CPU cycles, a poor fit for sustained, low-volume requests. I chose REST to query the semantic model on interactive compute, with its separate capacity smoothing, and let a FastAPI app use an authorized backend outside Fabric notebooks.

One query contract, reusable backends

The builder describes measures, groupings, filters, and sort order in Python. My compiler turns that request into DAX. The same query contract can run through a Fabric notebook backend or a REST backend, so the caller can choose the execution path for its environment without rewriting the query. REST gives our custom app an execution path outside the notebook runtime.

result = ( model.query() .measure("Example Total") .group_by("Date[Year]") .where("Date[Year]", "in", [2025, 2026]) .order_by("Date[Year]") .execute(backend) ) df = result.to_pandas()
Illustrative syntax. Package, configuration, property, measure, and table names in these examples are generic placeholders.

The current release builds and executes queries. Model-aware validation is next: it does not yet check that a measure or column exists before sending a request.

Parallelism matters

The underwriting workflow needs several independent reads from two models. I added async execution so those reads can run in parallel through one reusable backend instance. The queries describe what to fetch; the backend handles execution. The example below runs financial and occupancy queries together.

import asyncio from semantic_connect import Model from semantic_connect.backends import AsyncDaxBackend financials = Model.from_config("example_financial_model") operations = Model.from_config("example_operations_model") PROPERTIES = ["Example Property A", "Example Property B"] financial_query = ( financials.query() .measure("Actual Amount") .measure("Planned Amount") .group_by("Property[Name]") .where("Property[Name]", "IN", PROPERTIES) .where("Period[Selection]", "=", "Year to date") ) operations_query = ( operations.query() .measure("Utilization Rate") .measure("Available Unit Count") .group_by("Property[Name]") .where("Property[Name]", "IN", PROPERTIES) ) async def main() -> None: backend = AsyncDaxBackend.from_env() financial_result, operations_result = await asyncio.gather( financial_query.execute_async(backend), operations_query.execute_async(backend), ) print(financial_result.to_pandas()) print(operations_result.to_pandas()) asyncio.run(main())

An open-source release is in development

I am also developing an open-source version for release. The backend and CLI are independent of Trinity's models, so other companies using Microsoft Fabric could configure the tool for their own semantic models. The internal underwriting app is one application of that foundation.

Next: validation before execution

I plan to add model-snapshot validation so the library can check measures, columns, filters, and groupings before generating DAX. Typed references and generated interfaces would build on that foundation.

That is also the direction for an improved internal semantic MCP server. In our use, existing Power BI and Fabric IQ integrations can spend minutes generating and correcting DAX. I want agents to work through a validated query contract. The current library provides the builder and execution layer; the validator and improved MCP server remain future work.
