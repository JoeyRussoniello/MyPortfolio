Semantic Connect

A way to read governed Power BI measures from Python without writing DAX, built for web apps and AI agents.

StatusInternal v0 release
StackPython, DAX, Fabric, Power BI
FocusModel access without notebook-only auth

The problem

Trinity's reporting lives in Microsoft Fabric semantic models, and the easy access paths were not good enough. sempy is the obvious choice inside a Fabric notebook, but it is a notebook-centric tool, not a general-purpose way to serve semantic-model data to custom web applications outside the Fabric ecosystem. It also does not support the service-principal and OBO flows we rely on in production. The alternative route is direct lakehouse access through database queries, which is a different architecture and still burns the same finite background capacity as the data engineering workload.

The result was a practical gap: internal analyses and AI workflows could either query the semantic model or fit the platform's auth and capacity constraints, but not both. We needed a path that stayed interactive, reused the model's cached definitions, and did not force every request through the same background pool.

The approach

Semantic Connect is a Python query layer built for that gap. It gives a clean builder pattern for asking a semantic model for a set of measures, dimensions, filters, and sort order, then turns that request into the right DAX for the backend. The same query contract can run against a Fabric notebook path or a REST path, depending on the deployment requirements.

That matters because the underlying issue was not just a missing library. It was the interaction between auth, model access, and compute. The layer lets an application ask for governed data by name instead of hand-wiring DAX strings in each call site.

result = ( model.query() .measure("Revenue") .group_by("Calendar[Year]") .where("Calendar[Year]", "in", [2025, 2026]) .order_by("Calendar[Year]") .execute(backend) ) df = result.to_pandas()
Illustrative. The measure and column names are examples.

Parallelism matters

Once the query layer existed, the next win was concurrency. The same abstraction can fan out multiple model reads in parallel, which matters on both MCP-style integrations and static workflows that need several measures or groupings in one burst.

import asyncio from trinity_query import Model from trinity_query.backends import AsyncDaxBackend financials = Model.from_config("financials_rollup") operations = Model.from_config("operations") PROPERTIES = ["Arrive Hollywood", "Arrive Danbury"] noi = ( financials.query() .measure("NOI Actual") .measure("NOI Budget") .group_by("Dim_Property[Property Name]") .where("Dim_Property[Property Name]", "IN", PROPERTIES) .where("'Date Filters'[Date Filter]", "=", "YTD") ) occupancy = ( operations.query() .measure("Occupancy % Today") .measure("Rentable Unit Count Today") .group_by("DIM_PROPERTY[PROPERTY_NAME]") .where("DIM_PROPERTY[PROPERTY_NAME]", "IN", PROPERTIES) ) async def main() -> None: backend = AsyncDaxBackend.from_env() noi_result, occupancy_result = await asyncio.gather( noi.execute_async(backend), occupancy.execute_async(backend), ) print(noi_result.to_pandas()) print(occupancy_result.to_pandas()) asyncio.run(main())

How it is used

In production, this is already part of internal AI-analysis workflows. A common example is underwriting analysis: the model pulls a property's metrics, compares them with nearby holdings using geographic distance and market context, and checks whether the assumptions still hold in that market. The underlying semantic query is not hand-written at the point of use; it is defined once in code and executed through the chosen backend.

That pattern also scales for async calls. A single backend instance can be reused across multiple queries, so the app can run independent reads in parallel without rebuilding its connection state each time.

Why this backend model

The key design choice was to keep reads on the semantic model and away from heavy database-style execution. The REST path keeps queries interactive, it has better parallelism and batching than notebook-only access, and it avoids the finite background resource burden from a steady stream of direct database traffic.

The result is a small abstraction that sits in the gap between the application and the model. It is not trying to replace the model. It gives the rest of the system a stable, testable way to ask for governed numbers instead of letting each caller improvise its own queries.

What comes next

The next phase is the model validator: a schema-aware pass that compares the requested measures, filters, and groupings against the semantic model before any DAX is generated. That is where the project goes from a reliable internal v0 to a more opinionated platform layer, with typed references and generated interfaces that an agent or a UI can safely rely on.
